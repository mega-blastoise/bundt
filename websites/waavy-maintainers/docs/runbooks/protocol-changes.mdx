# Changing the Protocol

The host protocol is waavy's most important contract: hosts in other
languages implement it by hand. Every change touches the same set of places.

## Checklist for any protocol change

- [ ] `src/core/protocol.ts` (schemas) or `src/core/errors.ts` (codes)
- [ ] behaviour + tests in `test/cli.test.ts` and/or `test/serve.test.ts`
- [ ] `packages/waavy/docs/PROTOCOL.md`
- [ ] the generated JSON Schema (`dist/protocol.schema.json`) — regenerated by
      `bun run build`; `crates/waavy/tests/schema.rs` validates the Rust types
      against it
- [ ] `crates/waavy/src/protocol.rs` (+ builder method, + tests)
- [ ] consumer docs: `websites/waavy-docs/docs/reference/protocol.mdx` (and
      `errors.mdx`, `cli.mdx` as relevant)
- [ ] `CHANGELOG.md`

## Adding an optional request field (non-breaking)

1. Add it to `RenderRequestSchema` with a default or as optional. The schema
   is strict, so older waavy versions reject requests that use the new field
   with `INVALID_REQUEST` — document the minimum version in PROTOCOL.md.
2. If it maps to a CLI flag, add the flag in `cli/index.ts`, wire it in
   `cli/render-request.ts`, and add it to `REQUEST_FLAGS` so it conflicts
   with `--stdin`.
3. Add a builder method to the Rust `RenderRequest` with
   `skip_serializing_if` so old servers aren't sent the field unless used.

## Adding an error code (non-breaking)

1. Add the entry to `ERROR_CODES` with an exit status (unused, grouped by
   category: 1x request, 2x render, 3x release, 4x build, 70 internal) and an
   HTTP status.
2. `src/core/errors.test.ts` checks statuses are well-formed; add a contract
   test that produces the code.
3. Add the variant to the Rust `ErrorCode`, `KNOWN`, `as_str`,
   `exit_status`, `http_status`. Older crates see `ErrorCode::Unknown(…)`,
   which is why unknown-code tolerance is part of the contract.

## Adding a response header or log field (non-breaking)

Name headers `Waavy-…`. Document them; never make a client depend on a
header being present in older versions.

## Breaking changes

Anything that changes the meaning of an existing field, removes one, or
changes success/failure semantics:

1. bump `PROTOCOL_VERSION` (requests with the old `v` are rejected);
2. this also changes the JSON Schema `$id`s and the manifest's
   `protocolVersion`, so **every existing release must be rebuilt**
   (`VERSION_MISMATCH` otherwise);
3. ship it in a **minor** version with a migration note;
4. update the Rust crate's `PROTOCOL_VERSION` and types in the same release.

Prefer additive designs. If a change can be an optional field with the old
behaviour as default, it isn't breaking.

## Release ABI and manifest changes

The same logic applies to `RELEASE_ABI_VERSION` (the `release` export of
`server/entry.js`) and `MANIFEST_VERSION`. Remember that a release contains
its *own* copy of waavy's code: a runtime may load releases built by other
waavy versions. Keep the ABI to plain data and functions.
